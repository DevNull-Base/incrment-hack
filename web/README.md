# CRM ИТ-Школы РТК (lct-crm)

Система контроля взаимодействия с учебными заведениями для ИТ-Школы Ростелекома.

Кейс хакатона **Leaders of Digital Transformation (LCT)**: управление вузами, взаимодействиями (workflow-шаблоны B2B/B2C), программами, потоками обучения и документами.
Бекенд-контракт — [`openapi.json`](openapi.json).

## Быстрый старт

```bash
npm ci
npm run dev        # http://localhost:5173
```

Без файла `.env` интерфейс работает автономно: демо-вход по тестовым аккаунтам
и данные из моков стора, запросов к бэкенду нет.

### Режимы

| Режим | Как включить | Вход | Данные |
|---|---|---|---|
| Автономный (по умолчанию) | без `.env` | демо-форма, `TEST_ACCOUNTS` | моки стора |
| С бэкендом | `cp .env.example .env` | Keycloak (PKCE) → `GET /auth/me` | API бэкенда (`VITE_DATA_SOURCE=api`) |
| Стенд | переменные задаёт CI | Keycloak | API бэкенда |

Для режима с бэкендом из корня репозитория поднимается стек
(`docker compose --profile app up -d`, см. корневой README). Порт 5173 зафиксирован
(`strictPort`): он прописан в `redirect_uri` клиента `crm-frontend` Keycloak.

### Переменные сборки (`.env.example`)

| Переменная | Назначение |
|---|---|
| `VITE_API_TARGET` | адрес бэкенда для прокси дев-сервера (`/api`, `/socket.io`); в сборку не попадает |
| `VITE_KEYCLOAK_URL` | адрес Keycloak; задан — вход через Keycloak, не задан — демо-вход |
| `VITE_KEYCLOAK_REALM` | realm, по умолчанию `rtk-crm` |
| `VITE_KEYCLOAK_CLIENT_ID` | публичный клиент, по умолчанию `crm-frontend` |
| `VITE_DATA_SOURCE` | `api` — данные с бэкенда; `mock` (по умолчанию) — демо на моках |

Значения читаются в [`src/shared/config.ts`](src/shared/config.ts).

### Тестовый вход

Демо-режим (без Keycloak):

| Email | Пароль | Роль |
|---|---|---|
| admin@rtk.ru | admin123 | ADMIN |
| ivanov@rtk.ru | manager123 | MANAGER |
| user@rtk.ru | user123 | USER |

С Keycloak — учётные записи realm (`kam.ivanova`, `manager.petrov`, `admin.sidorov`),
пароли в разделе «Учётные записи стенда» корневого README.

Роли: **USER** — КАМ (операционная работа со своими заявками), **MANAGER** — руководитель менеджеров (команда, модерация, эскалации), **ADMIN** — технический администратор (полный доступ + админ-раздел).

## Вход и сессия

Вход — Authorization Code + PKCE, код [`src/shared/auth/keycloak.ts`](src/shared/auth/keycloak.ts):

1. «Войти» на `/login` → страница Keycloak; путь, с которого пришёл пользователь, запоминается.
2. Keycloak возвращает на `/` с кодом; `bootstrap()` стора до первого рендера меняет код
   на токены и восстанавливает исходный путь.
3. Профиль и роль — из `GET /api/v1/auth/me`; `RequireAuth`/`RequireRole` работают как раньше.
4. Токен обновляется заранее (60% срока жизни) и согласованно между вкладками;
   на 401 клиент API обновляет токен и повторяет запрос один раз, иначе — экран входа
   с сообщением «Сессия истекла».
5. «Выйти» завершает сеанс и в Keycloak (`end_session`).

Токены лежат в `localStorage` (`crm_access_token` и др.) — клиент API читает их оттуда.

## Данные с бэкенда (`VITE_DATA_SOURCE=api`)

После входа `loadData()` стора ([`api-data.ts`](src/app/store/api-data.ts)) загружает всё,
что нужно интерфейсу, постранично (не больше 200 записей за запрос) и с учётом роли:
разделы, которые бэкенд отдаёт только администратору (пользователи, аудит), у других
ролей не запрашиваются. Пока данные грузятся — экран «Загрузка данных…», ошибка — «Повторить».

| Раздел | Источник |
|---|---|
| Вузы, программы, продукты, направления, вендоры | `/catalog/*`; контакты и договоры вуза — по запросу страницы |
| Взаимодействия (канбан, карточка) | `/engagements`; переход — `POST …/transition` с `If-Match`, заметки, файлы, хронология, архив, переназначение |
| Этапы (колонки, прогресс, воронка) | определение действующего шаблона процесса сегмента — [`workflow-stages.ts`](src/app/workflow-stages.ts) |
| Редактор флоу | `/workflow/templates`: черновик следующей редакции → предпросмотр → публикация со сопоставлением этапов |
| Уведомления | `/notifications` (+ опрос раз в минуту), прочтение; политика и каналы — «Настройки» (ADMIN) |
| Календарь | `/calendar/tasks` (невыполненные + выполненные за 30 дней), `/calendar` окнами по 90 дней |
| Лента «мои действия» | `/activity/feed` |
| Заявки на обучение | B2C-взаимодействия (маршрут прямых продаж) |
| Потоки обучения | `/catalog/streams` — ранжирование программ, каталог курсов, карточки вуза и программы |
| Встречи | `/engagements/{id}/meetings` — карточка взаимодействия; в календаре — вид `MEETING` |
| Заметки по вузу | `/catalog/universities/{id}/notes` вместе с заметками взаимодействий вуза |
| Договоры и лицензии | в карточке вуза (`/catalog/universities/{id}/contracts`) |
| Документы | реестр вложений взаимодействий |
| Пользователи, аудит, персоны, интеграции, импорт | `/admin/users`, `/audit` (+ verify), `/persons`, `/integration/*`, `/import` |
| Отчёты (Аналитика) | `POST /reports`: небольшой — сразу файлом, объёмный — задача worker |
| Справка | руководства бэкенда `/guides` |

**Нет в API:** статусы согласования документов (в режиме API документ — вложение
взаимодействия) и чат — он остаётся демо на моках. Отдельного раздела лицензий нет:
лицензии видны в договорах вуза. История запросов к бэкенду —
[docs/заметки-для-бекендера.md](docs/заметки-для-бекендера.md).

## Снимки для встроенной справки

Руководства (`../docs/guides`) иллюстрированы снимками экранов — этого требует
ТЗ. После заметных изменений интерфейса снимки пересобираются одной командой
при запущенных фронтенде, бэкенде и Keycloak на базе, наполненной сидом:

```bash
npm run guide:screenshots
```

Скрипт входит демонстрационными учётными записями (переопределяются
переменными `GUIDE_*`), снимает экраны установленным Edge (`GUIDE_BROWSER=chrome`
— Chrome) и складывает PNG в `docs/guides/images`. Бэкенд отдаёт их по
`/api/v1/guides/images/{файл}` без входа — на снимках только данные наполнения.

## Развёртывание

Сборку выполняет CI ([`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml)):
`npm ci` → `npm run lint` → `npm test` → `npm run build` с переменными стенда.
Статика `dist/` уезжает на сервер и раздаётся Caddy с того же домена, что и API
(`/api/*` и `/socket.io/*` проксируются на бэкенд, остальное — SPA с fallback на `index.html`).
Файлы `assets/*` кэшируются навсегда (хэш в имени), `index.html` — `no-cache`.
Подробности — [`deploy/README.md`](../deploy/README.md).

## Архитектура UI

### Layout

```
┌──────────────────────────────────────────┐
│  Header (на всю ширину)                 │
├──────────┬───────────────────────────────┤
│          │                               │
│ Sidebar  │  Main content (Outlet)        │
│          │                               │
└──────────┴───────────────────────────────┘
```

- **Header** — фиксирован вверху, перекрывает всю ширину экрана
- **Sidebar** — под хедером слева; два режима описаны ниже

### Sidebar: два режима

| Режим | Когда | Ширина | Навигация |
|---|---|---|---|
 | **Широкий** | 1 экран (без split) | 240px (15rem) | Все пункты видны сразу, сгруппированы по секциям с заголовками |
 | **Узкий** | Split-screen (2 панели) | 52px | Вертикальный текст (файловые вкладки), наведение → выдвижное меню справа |

### Split-screen

Кнопка **«Разделение экрана»** в хедере (или `Ctrl+\`) делит экран на две независимые панели: слева — текущая страница, справа — экран выбора. У каждого окна свой сайдбар. Состояние живёт в query `?l=&r=&s=` — перезагрузка и «назад/вперёд» работают.

**Как работает навигация внутри split:**

1. `SplitContext` хранит панели в query `?l=&r=&s=` и перехватывает `history.pushState` / `replaceState` при включённом split
2. Любая навигация (`<Link>` или `navigate()`) пишется в параметр активной панели (`leftPage` / `rightPage`), а URL контейнера сохраняется
3. Активная панель определяется по `onMouseDown` (реф `activeSideRef`, синхронный)
4. Каждая панель рендерит контент через `<Routes location={path}>` — detail-роуты с `:id` работают корректно (`useParams()` возвращает параметры)

Ключевые файлы:
- `src/components/SplitContext.tsx` — состояние + перехват навигации
- `src/components/SplitScreenLayout.tsx` — две панели, divider, lazy-роуты
- `src/components/SplitToggle.tsx` — кнопка «Разделение экрана» в хедере
- `src/layouts/SidebarV2.tsx` — широкий и узкий режимы сайдбара
