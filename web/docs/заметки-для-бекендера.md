## Фильтры и сортировки (§4)

Параметры названы по соглашению API (`search`, `sortOrder`), а не `q` и `dir`:

```
GET /catalog/universities?search=<название|ИНН|город>&region=&activeOnly=
    &sortBy=name|createdAt|engagementCount&sortOrder=asc|desc
GET /catalog/programs?search=<название|описание>&source=&directionId=&universityId=
    &hoursMin=&hoursMax=&audienceCategory=&hasStreams=true|false
    &sortBy=name|hoursTotal|students&sortOrder=asc|desc
```

- `universityId` у программ — программы, по которым есть потоки в этом вузе;
- `hasStreams` — есть ли идущие или запланированные потоки;
- `sortBy=students` — по числу обучающихся сейчас (сумма по потокам `ACTIVE`).

Фронт по-прежнему загружает каталоги целиком и фильтрует на месте (каталоги — десятки
записей); серверные фильтры нужны внешним потребителям и большим каталогам.

## Значения перечислений

Для полей из §2–§3 значения в API — те, под которые собран фронт: `connected`,
`sz-rt`, `state-project`. У потоков и встреч — как во всём API, верхним регистром
(`ACTIVE`, `SCHEDULED`); фронт переводит их в свои строчные в `app/store/api-data.ts`.

## Что осталось на фронте без бэкенда

- **Чат** — демо на моках, по решению заказчика реализуется позже.
- **Реестр документов** собирается запросами вложений по каждому видимому
  взаимодействию (по 6 параллельно). На десятках заявок это незаметно; при сотнях
  понадобится общий список вложений с отбором по области видимости.
- **Согласование документов** (черновик → согласование → подписан) — в режиме API
  документ = вложение взаимодействия, статуса согласования у него нет.
