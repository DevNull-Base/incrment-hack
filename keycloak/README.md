# Конфигурация Keycloak

Файл `realm-export.json` импортируется автоматически при первом старте контейнера
(`start-dev --import-realm`), поэтому стенд поднимается одной командой без ручной
настройки через административную консоль.

> **Важно:** импортёр Keycloak использует строгую десериализацию и отвергает любые
> незнакомые поля. Комментарии внутри JSON (ключи вида `_comment`) приводят к отказу
> старта с ошибкой `Unrecognized field`. Поэтому пояснения вынесены сюда.

## Состав realm

**Realm:** `rtk-crm`

### Клиенты

| Клиент | Тип | Назначение |
|---|---|---|
| `crm-backend` | конфиденциальный | Ресурсный сервер. Проверяет токены, сам их не выпускает. Потоки входа отключены. |
| `crm-frontend` | публичный | SPA. Authorization Code Flow + PKCE (S256). |

На клиенте `crm-frontend` настроен маппер **`audience-crm-backend`**. Без него в токене
не будет `aud=crm-backend`, и бэкенд отклонит такой токен как предназначенный другому
сервису — это самая частая причина ошибки `CRM-AUT-0003` при первой настройке.

`directAccessGrantsEnabled` на `crm-frontend` включён намеренно: он позволяет получать
токен по логину и паролю без браузера, что необходимо нагрузочным тестам k6 и
автотестам. **В production-realm этот поток подлежит отключению.**

### Роли

| Роль | Кто это | Права |
|---|---|---|
| `USER` | КАМ — менеджер по вузам | Работа со своей выборкой данных |
| `MANAGER` | Руководитель | Данные подчинённых, переназначение ответственных |
| `ADMIN` | Администратор платформы | Полный доступ, управление правами и видимостью |

### Политики безопасности

Настроены в соответствии с требованиями к защите информации:

- парольная политика: не менее 12 символов, верхний и нижний регистр, цифра,
  спецсимвол, запрет совпадения с логином, история последних 3 паролей;
- защита от подбора: блокировка после 5 неудачных попыток с нарастающей задержкой;
- срок жизни access-токена — 15 минут, простой сессии — 30 минут;
- **регистрация событий включена** (`eventsEnabled`, `adminEventsEnabled`, хранение
  90 суток). Без неё события входа, выхода и неудачных попыток не сохранялись нигде:
  Keycloak по умолчанию их не пишет, а приложение видит только успешные обращения.
  Прикладной журнал фиксирует начало сеанса (`LOGIN`) и отказ деактивированной
  учётной записи (`LOGIN_DENIED`), Keycloak — попытки подбора пароля и изменения
  в самих учётных записях. Полная картина складывается только из обоих источников;
- **второй фактор для роли ADMIN**: политика TOTP включена в realm, а учётной записи
  администратора назначено обязательное действие `CONFIGURE_TOTP`. Привилегированный
  доступ, защищённый одним паролем, — типовая точка компрометации; рядовым
  пользователям второй фактор не навязывается.

### Что отличает демонстрационный realm от боевого

| Параметр | Здесь | В production |
|---|---|---|
| `sslRequired` | `external` | `all` |
| `directAccessGrantsEnabled` на `crm-frontend` | включён (нужен нагрузочным тестам) | отключить |
| Демонстрационные пользователи и пароли | в файле | удалить, завести реальных |
| `redirectUris` / `webOrigins` | localhost | домены стенда |
| Второй фактор | обязателен для ADMIN | рассмотреть и для MANAGER |

## Демонстрационные учётные записи

Пароли соответствуют политике realm. **Подлежат замене при реальном развёртывании.**

| Логин | Роль | Пароль |
|---|---|---|
| `kam.ivanova` | USER | `Kam#2026demo` |
| `kam.orlov` | USER | `Kam#2026demo` |
| `manager.petrov` | MANAGER | `Mgr#2026demo` |
| `admin.sidorov` | ADMIN | `Adm#2026demo` |

Административная консоль Keycloak: http://localhost:8080 (`admin` / `admin`).

## Получение токена для тестирования

```bash
curl -s -X POST http://localhost:8080/realms/rtk-crm/protocol/openid-connect/token \
  -d grant_type=password \
  -d client_id=crm-frontend \
  -d username=admin.sidorov \
  -d password='Adm#2026demo'
```

## Повторный импорт realm

Realm импортируется только при инициализации. Чтобы применить изменения в
`realm-export.json`, том Keycloak нужно пересоздать:

```bash
docker compose rm -sf keycloak
docker compose up -d keycloak
```

## Адреса Keycloak: внутренний и публичный

В docker compose бэкенд обращается к Keycloak по внутреннему имени
`http://keycloak:8080`, а браузер — по `http://localhost:8080`. Токен при этом
выпускается с `iss`, равным **публичному** адресу.

Поэтому в конфигурации приложения разведены две переменные:

- `KEYCLOAK_BASE_URL` — внутренний адрес, по нему забираются ключи (JWKS);
- `KEYCLOAK_PUBLIC_URL` — публичный адрес, с ним сверяется `iss` токена.

Без этого разделения корректные токены отклонялись бы проверкой issuer.
