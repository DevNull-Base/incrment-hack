# Нагрузочное тестирование

Техническое задание задаёт три числа: отклик интерфейса не более секунды,
50 параллельных пользователей и не менее 10 параллельных отчётов разной
сложности. На сессии вопросов и ответов заказчик попросил предусмотреть
«300 и более пользователей» и приложить раздел о масштабировании. Ниже —
замеры на объёме данных, заведомо большем ожидаемого, и выводы из них.

Замеры проведены 29 сентября 2026 года.

## Итог в цифрах

| Что проверялось | Результат |
|---|---|
| 50 параллельных сессий (требование ТЗ), 1 экземпляр API | худший p95 — **262 мс**, ошибок нет |
| 300 параллельных сессий, 2 экземпляра API | худший p95 — **899 мс**, ошибок нет |
| 300 параллельных сессий, 4 экземпляра API | худший p95 — **728 мс**, 817 запросов в секунду |
| Масштабирование 1 → 2 → 4 экземпляра | **364 → 648 → 817** запросов в секунду (×1,8 и ×2,2) |
| 10 параллельных отчётов (требование ТЗ), 1 → 2 → 4 фоновых процесса | **28 → 41 → 61** готовый отчёт в минуту, ошибок нет |
| Один отчёт на 50 000 строк | xlsx — **7,6 с**, csv — **6,8 с** до готового файла |
| Отчёт на ~1 000 строк | **0,2 с**, файл сразу в ответе |
| Исправлено по итогам замеров | поиск: **120 → 6 мс** процессора базы на запрос; переход по этапу при 100 сессиях: p95 **1 076 → 751 мс**, при 300 на 4 экземплярах — **2 166 → 1 556 мс**; вход в интерфейс — **на 40% быстрее** |

Во всех прогонах — **ноль ошибок**: все ответы 200, 201 и 202, кроме штатных
отказов 409 при одновременной правке одной карточки (о них ниже).

## Как измерялось

### Объём данных

Демонстрационный сид заводит 81 заявку: на таком объёме любой запрос быстр,
отчёты не доходят до очереди, и замер ничего не говорит о работе на годах
накопленной истории. Поэтому замеры идут на отдельной базе, доведённой
скриптом [load/bulk-data.sql](../load/bulk-data.sql) до масштаба с запасом
на порядок: по ТЗ это около 20 КАМов и около 700 вузов, то есть единицы
тысяч заявок.

| Данные | Объём |
|---|---|
| Заявки | **50 081** (40 000 B2B и 10 000 B2C сверх сида) |
| Журнал переходов | 252 338 записей |
| Лента действий | 252 603 события |
| Заметки | 50 076 |
| Вузы | 500 |
| Сотрудники | 48 (44 КАМа и руководителя сверх сида) |

История строится по маршрутам действующих процессов — с теми же подписями
этапов, сроками и журналом, что оставляет интерфейс. Данные вымышленные.

### Условия

| Параметр | Значение |
|---|---|
| Оборудование | AMD Ryzen 7 5700X — 8 ядер, 16 потоков; 32 ГБ |
| Приложение | `NODE_ENV=production`, журнал `info` в JSON, антивирус включён |
| Инфраструктура | PostgreSQL 17, Redis 7, MinIO — в Docker на той же машине |
| Генератор нагрузки | [load/run.mjs](../load/run.mjs), 4 процесса, на той же машине |
| Несколько экземпляров | [load/cluster.mjs](../load/cluster.mjs) — балансировка соединений по кругу |

Клиент, API и база делят одни 16 потоков, поэтому инструмент печатает, сколько
ядер занял каждый: API, фоновый процесс, PostgreSQL (по счётчику cgroup
контейнера) и сам генератор нагрузки. Без этой раскладки нельзя сказать,
во что упёрлась система. На раздельных серверах числа будут лучше:
требования проверяются в заведомо невыгодной обстановке.

Ограничение частоты обращений — защитная мера, а не предел
производительности, поэтому на время замера оно поднимается
(`THROTTLE_LIMIT=100000`, `THROTTLE_EXPORT_LIMIT=10000`). Инструмент
отдельно предупреждает, если в замер попали отказы 429.

### Сценарии

**«Рабочий день».** Каждая сессия по кругу открывает список заявок (случайную
страницу), карточку, заметки к ней, ищет вуз по названию, проверяет счётчик
уведомлений, листает каталог вузов, ленту действий и задачи календаря. Сессии
идут от всех четырёх ролей, карточки берутся из видимых этой роли. Тело каждого
ответа вычитывается полностью, иначе замер показал бы время до заголовков.

**«С записью».** К рабочему дню добавляются новая заметка и переход по этапу.
Переход выбирается из доступных карточке и отправляется с версией, прочитанной
вместе с ней, — как это делает интерфейс.

**«Отчёты».** Десять параллельных заказчиков отчётов. Отчёт выбирается случайно
из пяти видов, от ~1 000 до 50 000 строк, в форматах csv, xlsx, xls и pdf.
Для отчёта из очереди замеряется время до готового файла, включая скачивание.
Заголовок у каждого отчёта свой, иначе повторный запрос отдавался бы из кэша
готовых файлов, и замер показывал бы кэш, а не расчёт.

**«Вход».** Всё, что интерфейс загружает сразу после входа: профиль, каталоги,
заявки постранично, уведомления, задачи и ленту.

### Что такое «сессия»

Сессия работает **без пауз**: следующий запрос уходит сразу после ответа
на предыдущий. Человек между действиями читает карточку и печатает, поэтому
одна сессия — это нагрузка от многих людей. Если принять, что активно
работающий сотрудник обращается к API в среднем раз в 10 секунд, то
**364 запроса в секунду одного экземпляра — это порядка 3 600 одновременно
работающих людей**, а 817 запросов в секунду четырёх экземпляров — порядка
8 000. Это оценка при названном допущении, а не замер.

## Что нашли и исправили

**Поиск по заявкам.** Первый прогон на 50 000 заявок показал, что поиск
стоит **120 мс процессора базы на каждый запрос** и упирается в 66 запросов
в секунду при загрузке восьми ядер. Условие «вуз с таким названием» стояло
внутри выборки заявок через связь с таблицей вузов, и такое «ИЛИ» не может
опереться ни на один индекс: база на каждый запрос перебирала все заявки.

Теперь подходящие вузы находятся отдельным запросом по триграммному индексу
(их сотни), а заявки отбираются по `university_id`. Для поиска по контрагенту
и заголовку добавлены триграммные индексы — миграция
`20260929120000_engagement_search_indexes`. Результаты поиска совпадают
с прежними, это проверено на выборках и закреплено тестом
`test/unit/engagement-search.spec.ts`.

| | Было | Стало |
|---|---|---|
| Процессор базы на один поиск | 120 мс | 6,3 мс |
| Поиск, запросов в секунду (8 потоков) | 66 | 271 |
| Процессор базы на запрос «рабочего дня» | 12,4 мс | 7,7 мс |
| Загрузка базы при 50 сессиях | 5,3 ядра | 2,8 ядра |

Именно это освободило базе запас, благодаря которому второй и четвёртый
экземпляры API вообще дают прирост.

**Журнал аудита.** Журнал — хэш-цепочка, и запись в него идёт строго
по очереди под единой блокировкой. Блокировка удерживалась на время четырёх
обращений приложения к базе (взять блокировку, прочитать предыдущий хэш,
вставить, завершить транзакцию), и под нагрузкой каждое ждало очереди событий
Node: журнал пропускал около 40 записей в секунду на всю систему, и на нём
стоял в очереди каждый переход по этапу. Теперь всё это делает одна функция
базы `audit_append` (миграция `20260929140000_audit_append_function`):
блокировка держится время одной вставки внутри PostgreSQL. Хэш база считает
по той же формуле от той же канонической строки, что и приложение, — штатная
проверка целостности после нагрузочного прогона подтвердила все 1 317 записей.

| Один экземпляр, 100 сессий «с записью» | Было | Стало |
|---|---|---|
| Переход по этапу, p95 | 1 076 мс | 895 мс |
| Переходов за минуту | 903 | 1 354 |
| Всего запросов в секунду | 313 | 365 |

(окончательные цифры перехода — в следующем пункте)

**Переход по этапу.** Один переход выполнял 39 SQL-операторов. Сокращено:

- определение процесса читалось из базы и проверялось схемой дважды на каждый
  переход (до транзакции и в карточке-ответе) и на каждую карточку. Редакцию,
  по которой ведутся заявки, изменить нельзя, поэтому её разбор теперь
  кэшируется (`WorkflowService.definitionOf`);
- правила уведомлений читались через upsert — транзакцию из нескольких
  операторов на каждое уведомление о переходе; теперь это одно чтение;
- интерфейс перед каждым переходом заново загружал карточку ради её версии,
  хотя открытая карточка уже в памяти. Теперь переход отправляется сразу; если
  версия устарела, карточка перечитывается и переход повторяется один раз —
  только если заявка стоит на том же этапе. Для пользователя это минус одна
  полная загрузка карточки (14 операторов) на каждом переходе.

Переход — 39 → 31 оператор на сервере, карточка — 15 → 14.

| Переход по этапу, p95 | Исходно | Стало |
|---|---|---|
| 1 экземпляр, 100 сессий «с записью» | 1 076 мс | **751 мс** |
| 4 экземпляра, 300 сессий «с записью» | 2 166 мс | **1 556 мс** |

Ошибок нет; целостность журнала аудита после прогонов подтверждена
(4 183 записи).

Попутно замер нашёл гонку. Заявку и экземпляр процесса Prisma читает разными
запросами, и переход другого пользователя, завершившийся между ними, давал
старую версию при новом этапе: проверка версии проходила, и человек вместо
«карточку изменил другой пользователь» (409) получал отказ по условиям чужого
этапа (422). Данные при этом не портились — запись защищена проверкой версии
в транзакции. Теперь этап берётся из той же строки, что и версия.

**Вход в интерфейс.** Интерфейс запрашивал список заявок дважды — активные
и все вместе с архивом, — чтобы вычесть одно из другого. Теперь признак архива
приходит в строке списка, и список запрашивается один раз: вход КАМа —
0,29 → 0,17 с, администратора на 50 000 заявок — 2,6 → 1,6 с.

## Известные пределы

**Переход по этапу — самая дорогая операция.** 31 SQL-оператор: транзакция
перехода, журнал аудита, карточка для ответа и уведомление. На машине,
загруженной до 100% (четыре экземпляра, 300 сессий «с записью»), p95
перехода — 1,6 с. Следующий резерв — загрузка связей карточки одним запросом
(`relationLoadStrategy: 'join'` в Prisma): сейчас каждая связь — отдельный
запрос, и карточка — это 14 обращений к базе.

**Интерфейс загружает список заявок целиком.** Канбан, отборы и поиск
на клиенте работают по загруженному списку — поэтому переключения мгновенны,
но вход администратора на 50 000 заявок занимает 2,6 с, а список ограничен
10 000 записей: сверх этого канбан администратора их не покажет. На ожидаемых
объёмах (единицы тысяч) предел не достигается; для десятков тысяч канбану
нужен серверный постраничный вывод по колонкам.

**Лента действий КАМа считает общий итог.** На каждой странице ленты точно
считается число событий пользователя: у КАМа из нагрузочного набора их
5 800, это 10–20 мс процессора базы. В реальном объёме истории у КАМа в десятки
раз меньше.

**Главный потребитель ресурсов — база.** На запрос «рабочего дня» уходит
около 8 мс процессора PostgreSQL против ~3 мс у самого API. Секционирования
журналов и реплики для чтения в системе сейчас нет — это следующие шаги,
если объём вырастет на порядок.

## Как масштабировать

Варианты, которые заказчик перечислил на сессии, подтверждены замерами.

**Экземпляры API.** Приложение не хранит состояния в памяти процесса: рабочий
контекст пользователя — в Redis и в базе, ограничение частоты обращений общее
для всех экземпляров, события канала обновлений между экземплярами разносит
Redis-адаптер socket.io. Второй экземпляр дал ×1,8, четвёртый — ×2,2 на одной
машине, где упор уже в процессор, общий с базой.

Поставка стенда сейчас поднимает один экземпляр API на порту 18080, за которым
стоит Caddy. Для нескольких экземпляров им даётся диапазон портов, а Caddy
перечисляет их все:

```yaml
# deploy/docker-compose.prod.yml, служба api
ports:
  - '127.0.0.1:18090-18093:3000'
```

```bash
docker compose -f deploy/docker-compose.prod.yml up -d --scale api=4
```

```caddyfile
reverse_proxy 127.0.0.1:18090 127.0.0.1:18091 127.0.0.1:18092 127.0.0.1:18093 {
	lb_policy ip_hash
	health_uri /health/ready
}
```

Привязка клиента к экземпляру (`ip_hash`) нужна каналу обновлений: socket.io
начинает соединение с длинных опросов, и запросы одного клиента должны
попадать в один экземпляр. Пул соединений с базой — 20 на экземпляр
(`DB_POOL_MAX`), PostgreSQL принимает 200: на четыре экземпляра и фоновые
процессы этого хватает.

**Фоновые процессы.** Отчёты, импорт и обмен считает отдельный процесс, и он
масштабируется независимо. Замер: 1 → 2 → 4 процесса дают 28 → 41 → 61 отчёт
в минуту, время до файла по всей базе — 46 → 37 → 23 с.

```bash
docker compose -f deploy/docker-compose.prod.yml up -d --scale worker=4
```

Регламентные задачи при этом не дублируются: рассылка напоминаний, очистка
по срокам хранения и отправка исходящих событий защищены блокировками.

**База данных — на отдельный сервер.** На одной машине с четырьмя экземплярами
она заняла 10,6 потока из 16. Отдельный сервер снимает конкуренцию
за процессор; дальше — реплика для чтения под отчёты и списки.

**Чего делать не нужно.** Наращивать параллельность внутри одного процесса:
предел экземпляра — одно ядро, и настройки его не сдвинут.

## Воспроизведение

```bash
# отдельная база: миграции, сид без файлов в хранилище, объём
docker exec crm-postgres psql -U crm -d postgres -c "CREATE DATABASE crm_load OWNER crm"
DATABASE_URL=postgresql://…/crm_load npx prisma migrate deploy
DATABASE_URL=postgresql://…/crm_load S3_ENDPOINT= npx tsx prisma/seed.ts
docker exec -i crm-postgres psql -U crm -d crm_load -v ON_ERROR_STOP=1 < load/bulk-data.sql

# приложение в режиме production, N экземпляров API и фоновый процесс
npm run build
API_INSTANCES=4 node --env-file=load.env load/cluster.mjs
APP_ROLE=worker node --env-file=load.env dist/worker.js

# замеры
node load/run.mjs --api http://localhost:3200 --users 300 --seconds 60 --procs 4 --monitor
node load/run.mjs --api http://localhost:3200 --scenario mixed --users 100 --procs 4 --monitor
node load/run.mjs --api http://localhost:3200 --scenario reports --users 10 --seconds 120 --monitor
node load/run.mjs --api http://localhost:3200 --scenario report-each --users 1
node load/run.mjs --api http://localhost:3200 --scenario login --users 4 --seconds 40
```

`load.env` — обычная конфигурация с `NODE_ENV=production`, отдельной базой
данных и базой Redis, поднятыми на время замера `THROTTLE_LIMIT`
и `THROTTLE_EXPORT_LIMIT`. Ключ `--out файл.json` сохраняет результат
вместе с раскладкой по ядрам.
