# Нагрузочное тестирование

Техническое задание задаёт три требования: отклик интерфейса не более секунды,
50 параллельных пользователей и не менее 10 параллельных отчётов разной
сложности. На сессии вопросов и ответов заказчик попросил предусмотреть
«300 и более пользователей» и приложить раздел о масштабировании. Ниже —
замеры на объёме данных, заведомо большем ожидаемого, и выводы из них.

Замеры проведены 29 сентября 2026 года на текущей версии из ветки `main`.

## Итог в цифрах

| Что проверялось | Результат |
|---|---|
| 50 параллельных сессий (требование ТЗ), 1 экземпляр API | худший p95 — **232 мс**, 421 запрос в секунду, ошибок нет |
| 300 параллельных сессий, 4 экземпляра API | худший p95 — **785 мс**, 758 запросов в секунду, ошибок нет |
| Пропускная способность на 1 → 2 → 4 экземплярах | **421 → 620 → 758** запросов в секунду |
| 100 сессий с записью (заметки и переходы), 1 экземпляр | переход по этапу: p95 — **905 мс**, заметка — **430 мс** |
| 10 параллельных отчётов (требование ТЗ), 1 → 2 → 4 фоновых процесса | **22 → 41 → 62** готовых отчёта в минуту, ошибок нет |
| Один отчёт на 50 000 строк | xlsx — **8,4 с**, csv — **7,4 с** до готового файла |
| Отчёт на ~1 100 строк | **0,19 с**, файл сразу в ответе |
| Вход в интерфейс | КАМ — **0,13 с**, руководитель — **0,37 с**, администратор со всеми 50 000 заявок — **1,0 с** |

Во всех прогонах **ни одной ошибки**: все ответы — 200, 201 и 202, кроме
штатных отказов 409 при одновременной правке одной карточки (о них ниже).
После прогонов с записью штатная проверка подтвердила целостность журнала
аудита: 3 296 записей, цепочка не нарушена.

## Как измерялось

### Объём данных

Демонстрационный сид заводит 81 заявку. На таком объёме любой запрос быстр,
отчёты не доходят до очереди, и замер ничего не говорит о работе с годами
накопленной истории. Поэтому замеры идут на отдельной базе, которую скрипт
[load/bulk-data.sql](../load/bulk-data.sql) доводит до масштаба с запасом
на порядок: по ТЗ это около 20 КАМов и около 700 вузов, то есть единицы
тысяч заявок.

| Данные | Объём |
|---|---|
| Заявки | **50 081**: 40 063 B2B и 10 018 B2C |
| Журнал переходов | 252 260 записей |
| Лента действий | 252 525 событий |
| Заметки | 50 076 |
| Вузы | 500 |
| Сотрудники | 48 |

История строится по маршрутам действующих процессов — с теми же подписями
этапов, сроками и журналом, что оставляет интерфейс. Данные вымышленные.

### Условия

| Параметр | Значение |
|---|---|
| Оборудование | AMD Ryzen 7 5700X — 8 ядер, 16 потоков; 32 ГБ |
| Приложение | Node.js 24, `NODE_ENV=production`, журнал `info` в JSON, антивирус включён |
| Инфраструктура | PostgreSQL 17, Redis 7, MinIO — в Docker на той же машине |
| Генератор нагрузки | [load/run.mjs](../load/run.mjs), 4 процесса, на той же машине |
| Несколько экземпляров | [load/cluster.mjs](../load/cluster.mjs) — балансировка соединений по кругу |

Клиент, API и база делят одни 16 потоков. Поэтому инструмент печатает, сколько
ядер занял каждый: API, фоновый процесс, PostgreSQL (по счётчику cgroup
контейнера) и сам генератор нагрузки. Без этой раскладки нельзя сказать,
во что упёрлась система. На раздельных серверах числа будут лучше: требования
проверяются в заведомо невыгодной обстановке.

Ограничение частоты обращений — защитная мера, а не предел
производительности, поэтому на время замера оно поднимается
(`THROTTLE_LIMIT=100000`, `THROTTLE_EXPORT_LIMIT=10000`). Инструмент
отдельно предупреждает, если в замер попали отказы 429. Перед серией
интерактивных прогонов API 20 секунд прогревается той же нагрузкой, прогрев
в замер не входит.

### Сценарии

**«Рабочий день».** Каждая сессия по кругу открывает список заявок (случайную
страницу), карточку, заметки к ней, ищет заявки по вузу, проверяет счётчик
уведомлений, листает каталог вузов, ленту действий и задачи календаря. Сессии
идут от всех четырёх ролей, карточки берутся из видимых этой роли. Тело каждого
ответа вычитывается полностью, иначе замер показал бы время до заголовков.

**«С записью».** К рабочему дню добавляются новая заметка и переход по этапу.
Переход выбирается из доступных карточке и отправляется с версией, прочитанной
вместе с ней, как это делает интерфейс.

**«Отчёты».** Десять параллельных заказчиков отчётов. Отчёт выбирается случайно
из семи вариантов объёмом от ~1 100 до 50 000 строк, в форматах csv, xlsx, xls
и pdf.
Для отчёта из очереди замеряется время до готового файла, включая скачивание.
Заголовок у каждого отчёта свой, иначе повторный запрос отдавался бы из кэша
готовых файлов и замер показывал бы кэш, а не расчёт.

**«Вход».** Всё, что интерфейс загружает сразу после входа: профиль, каталоги,
заявки постранично, уведомления, задачи и ленту.

### Что такое «сессия»

Сессия работает **без пауз**: следующий запрос уходит сразу после ответа
на предыдущий. Человек между действиями читает карточку и печатает, поэтому
одна сессия создаёт нагрузку многих людей. Если принять, что активно
работающий сотрудник обращается к API в среднем раз в 10 секунд, то **421
запрос в секунду одного экземпляра — это порядка 4 000 одновременно работающих
людей**, а 758 запросов в секунду четырёх экземпляров — порядка 7 500. Это
оценка при названном допущении, а не замер.

### Запись: заметки и переходы по этапам

| Обращение | 1 экземпляр, 100 сессий: p95 | 4 экземпляра, 300 сессий: p95 |
|---|---|---|
| Новая заметка | 430 мс | 832 мс |
| Переход по этапу | 905 мс | 1 760 мс |
| Карточка заявки | 496 мс | 904 мс |
| Всего запросов в секунду | 328 | 590 |
| Переходов за прогон | 1 282 | 1 847 |

Ошибок нет. Часть переходов получила 409: 34 из 1 282 на одном экземпляре,
111 из 1 847 на четырёх. Это две сессии одновременно двигали одну заявку,
и вторая получила отказ по версии карточки. Так работает штатная защита
от потери чужой правки, а не сбой.

Переход — самая дорогая операция: транзакция перехода (процесс, заявка,
экземпляр, журнал переходов, лента, исходящее событие для внешних систем),
запись в журнал аудита, карточка для ответа и уведомление ответственному —
всего 31 SQL-оператор. Журнал аудита — хэш-цепочка, и записи в него идут
строго по очереди. Поэтому блокировку, чтение предыдущего хэша и вставку
делает одна функция базы `audit_append`: блокировка держится только на время
одной вставки внутри PostgreSQL.

фоновый процесс, не отнимая процессор у пользователей.

**Десять параллельных отчётов — требование ТЗ.** Десять заказчиков в течение
двух минут непрерывно заказывают отчёты всех видов вперемешку:

| Фоновых процессов | Отчётов за прогон | В минуту | Вся база xlsx: до файла, среднее | Pdf: до файла, среднее | Ядер у фоновых процессов |
|---|---|---|---|---|---|
| 1 | 57 | 22 | 56,8 с | 22,1 с | 1,2 |
| 2 | 92 | 41 | 32,5 с | 8,3 с | 2,3 |
| 4 | 134 | **62** | **24,4 с** | **5,2 с** | 4,1 |

Ошибок нет. Один фоновый процесс занимает одно ядро, и десять одновременных
отчётов стоят к нему в очереди. Каждый добавленный процесс добавляет ядро
и сокращает ожидание: производительность растёт почти линейно. Небольшие
отчёты всё это время отдаются сразу: заказ отчёта на ~1 100 строк занимает
0,2–0,3 с при любой загрузке очереди.

### Вход в интерфейс

Сколько занимает первая загрузка интерфейса при 50 081 заявке в базе.
Интерфейс загружает видимые роли заявки целиком, постранично по 200:

| Роль | Видит заявок | Один вход, p50 | 20 непрерывных входов одновременно, p50 |
|---|---|---|---|
| КАМ | 1 148 | **0,13 с** | 1,6 с |
| Руководитель | 3 317 | **0,37 с** | 4,7 с |
| Администратор | 50 081 | **1,04 с** | 13,7 с |

«Один вход» — роль входит без соседей. Правая колонка — стресс-сценарий:
20 сессий на одном экземпляре повторяют вход без пауз, и каждый вход
администратора выкачивает все 50 000 заявок. Время входа растёт вместе
с числом видимых заявок — см. «Известные пределы».

## Известные пределы

**Переход по этапу — самая дорогая операция.** Это 31 SQL-оператор: транзакция
перехода, журнал аудита, карточка для ответа и уведомление. На машине,
загруженной до 100% (четыре экземпляра, 300 сессий «с записью»), p95
перехода — 1,8 с. Следующий резерв — загрузка связей карточки одним запросом
(`relationLoadStrategy: 'join'` в Prisma). Сейчас каждая связь загружается
отдельным запросом, и карточка — это 14 обращений к базе.

**Интерфейс загружает список заявок целиком.** Канбан, отборы и поиск
на клиенте работают по загруженному списку, поэтому переключения мгновенны.
Но вход администратора на 50 000 заявок занимает около секунды, а при
одновременных входах — больше. Кроме того, список ограничен 10 000 записей:
сверх этого канбан администратора заявки не покажет. На ожидаемых объёмах
(единицы тысяч) предел не достигается. Для десятков тысяч канбану нужен
серверный постраничный вывод по колонкам.

**Лента действий считает общий итог.** На каждой странице ленты точно
считается число событий пользователя. У КАМа из нагрузочного набора их около
5 800, поэтому лента — одно из самых медленных обращений «рабочего дня»
(p95 211 мс при 50 сессиях). В реальной истории у КАМа событий в десятки раз
меньше.

**Главный потребитель ресурсов — база.** На запрос «рабочего дня» PostgreSQL
тратит больше процессорного времени, чем сам API: на четырёх экземплярах
база занимает 8,4 потока против 3,2 у всех экземпляров API. Секционирования
журналов и реплики для чтения в системе сейчас нет — это следующие шаги,
если объём вырастет на порядок.

## Как масштабировать

Варианты, которые заказчик перечислил на сессии, подтверждены замерами.

**Экземпляры API.** Приложение не хранит состояния в памяти процесса: рабочий
контекст пользователя — в Redis и в базе, ограничение частоты обращений общее
для всех экземпляров, события канала обновлений между экземплярами разносит
Redis-адаптер socket.io. Второй экземпляр даёт ×1,5, четвёртый — ×1,8 на одной
машине, где упор уже в процессор, общий с базой.

Поставка стенда сейчас поднимает один экземпляр API на порту 18080, за которым
стоит Caddy. Для нескольких экземпляров им даётся диапазон портов, а Caddy
перечисляет их все:

```yaml
# deploy/docker-compose.prod.yml, служба api
ports:
  - '127.0.0.1:18090-18093:3000'
```

```bash
docker compose -f deploy/docker-compose.prod.yml up -d --scale api=4
```

```caddyfile
reverse_proxy 127.0.0.1:18090 127.0.0.1:18091 127.0.0.1:18092 127.0.0.1:18093 {
	lb_policy ip_hash
	health_uri /health/ready
}
```

Привязка клиента к экземпляру (`ip_hash`) нужна каналу обновлений: socket.io
начинает соединение с длинных опросов, и запросы одного клиента должны
попадать в один экземпляр. Пул соединений с базой — 20 на экземпляр
(`DB_POOL_MAX`), PostgreSQL принимает 200: на четыре экземпляра и фоновые
процессы этого хватает.

**Фоновые процессы.** Отчёты, импорт и обмен обрабатывает отдельный процесс,
и он масштабируется независимо. Замер: 1 → 2 → 4 процесса дают 22 → 41 → 62
отчёта в минуту, а отчёт по всей базе под той же нагрузкой готов за 56,8 →
32,5 → 24,4 с.

```bash
docker compose -f deploy/docker-compose.prod.yml up -d --scale worker=4
```

Регламентные задачи при этом не дублируются: рассылка напоминаний, очистка
по срокам хранения и отправка исходящих событий защищены блокировками.

**База данных — на отдельный сервер.** На одной машине с четырьмя
экземплярами она заняла 8,4 потока из 16. Отдельный сервер снимает
конкуренцию за процессор; дальше — реплика для чтения под отчёты и списки.

**Чего делать не нужно.** Наращивать параллельность внутри одного процесса:
предел экземпляра — одно ядро, и настройки его не сдвинут.

`load.env` — обычная конфигурация с `NODE_ENV=production`, отдельной базой
данных и базой Redis, поднятыми на время замера `THROTTLE_LIMIT`
и `THROTTLE_EXPORT_LIMIT`. Ключ `--out файл.json` сохраняет результат
вместе с раскладкой по ядрам, `--account логин` пускает все сессии от одной
учётной записи.
