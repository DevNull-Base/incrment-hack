# Стенд на сервере Epyc (Windows)

Развёртывание по коммиту в `main`: GitHub Actions выполняет проверки, доставляет
исходники и собранную статику по SSH, сервер собирает образ и перезапускает
контейнеры. Наружу смотрит только Caddy.

```
коммит в main
   └─ проверки на раннере      lint → сборка → тесты → фронтенд: lint, тесты, сборка
        └─ доставка по SSH     два архива + deploy.ps1
             └─ deploy.ps1 на сервере
                  ├─ распаковка исходников
                  ├─ сборка образа с тегом по SHA
                  ├─ миграции отдельной задачей
                  ├─ перезапуск api и worker
                  ├─ ожидание /health/ready
                  └─ переключение точки соединения на новую статику
```

Порядок шагов не случаен: статика переключается **после** того, как новый бэкенд
вышел в готовность. Иначе новый интерфейс какое-то время работал бы со старым API.
Если API не поднялся — статика остаётся прежней, а бэкенд откатывается на
предыдущий образ.

## Порты: почему конфликтов с Forgejo не будет

Из всего стека наружу процесса Docker публикуются **два** порта, и оба — на
петлевом интерфейсе:

| Сервис | Порт | Доступен |
|---|---|---|
| API | `127.0.0.1:18080` | только с самого сервера (для Caddy) |
| Keycloak | `127.0.0.1:18081` | только с самого сервера (для Caddy) |
| Postgres | — | внутренняя сеть Docker |
| Redis | — | внутренняя сеть Docker |
| MinIO | — | внутренняя сеть Docker |
| ClamAV | — | внутренняя сеть Docker |

Контейнеры общаются между собой по именам сервисов внутри своей сети, поэтому
Postgres стенда и Postgres Forgejo не пересекаются ни портом, ни именем: у стека
своё имя проекта (`incrment`), а значит свои имена контейнеров, сети и томов.

Проверить занятость портов до первого развёртывания:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 18080, 18081 -ErrorAction SilentlyContinue |
  Select-Object LocalAddress, LocalPort, OwningProcess
```

Пусто — порты свободны. Заняты — поменяйте `API_BIND_PORT` и `KEYCLOAK_BIND_PORT`
в `C:\www\incrment\.env` и соответствующие адреса в конфигурации Caddy.

## Подготовка сервера (один раз)

### 1. Каталоги

```powershell
New-Item -ItemType Directory -Force `
  C:\www\incrment\repo, C:\www\incrment\releases\web, `
  C:\www\incrment\uploads, C:\www\incrment\logs
```

### 2. Учётная запись для развёртывания

Развёртывание идёт по SSH под обычной учётной записью Windows. Два требования:

- она входит в группу **docker-users**;
- под ней же запущен **Docker Desktop**.

Второе важнее, чем кажется: Docker Desktop работает в пользовательском сеансе,
и SSH-сессия под другой учётной записью просто не увидит движок — `docker ps`
ответит «cannot connect». Проверять это надо до первого развёртывания:

```powershell
ssh -p <порт> <пользователь>@<хост> "docker ps"
```

Если ответ — список контейнеров, всё в порядке. Если ошибка подключения к
движку, вариантов два: разворачивать под той же учётной записью, под которой
работает Docker Desktop, либо перевести движок в режим службы (Docker Engine
в WSL2 без Desktop).

### 3. Ключ для CI

Ключ создаётся на любой машине, публичная часть кладётся на сервер:

```powershell
# на сервере, под учётной записью развёртывания
New-Item -ItemType Directory -Force "$env:USERPROFILE\.ssh"
Add-Content "$env:USERPROFILE\.ssh\authorized_keys" "<содержимое id_deploy.pub>"
```

**Если учётная запись состоит в администраторах**, OpenSSH на Windows читает не
её `authorized_keys`, а общий файл — это самая частая причина «ключ не
подходит, хотя всё сделано правильно»:

```powershell
Add-Content C:\ProgramData\ssh\administrators_authorized_keys "<содержимое id_deploy.pub>"
icacls C:\ProgramData\ssh\administrators_authorized_keys /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"
```

Приватный ключ уходит в секрет `SSH_PRIVATE_KEY`. Ключ сервера отдельно
заводить не нужно: workflow получает его сканированием (`ssh-keyscan`) перед
каждой доставкой и печатает отпечатки в журнал.

Если понадобится закрепить ключ, чтобы подмена сервера ломала развёртывание,
а не проходила незаметно, — заведите необязательный секрет `SSH_KNOWN_HOSTS`
с выводом команды:

```powershell
ssh-keyscan -p <порт> <хост>
```

Тогда полученный ключ сверяется с закреплённым, и при расхождении конвейер
останавливается до того, как что-либо уйдёт на сервер.

### 4. Настройки стенда

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File C:\www\incrment\repo\deploy\windows\new-env.ps1
```

Скрипт берёт образец `deploy\env.prod.example`, подставляет вместо каждого
«ЗАМЕНИТЬ_НА_ДЛИННЫЙ_ПАРОЛЬ» свой случайный пароль (общий пароль на базу,
Keycloak и хранилище означал бы, что утечка одного открывает всё), пишет файл
без метки порядка байтов — иначе docker compose не разберёт первую строку —
и заодно проверяет, виден ли Docker, есть ли `tar` и свободны ли порты.

Существующий `.env` скрипт не трогает: пароли из него уже разошлись по базам
и томам, и замена означала бы стенд, который больше не поднимется.

Одно исключение делает сам `deploy.ps1`: секрет подписи входящих вызовов
`INTEGRATION_WEBHOOK_SECRET`. Если его в `.env` нет либо там осталась метка
из образца, при выкладке он заменяется случайным значением. Секрет не связан
с данными в томах, поэтому замена безопасна, а без неё приём событий LMS
и сайта был бы открыт: метка лежит в публичном репозитории, и подписать ею
вызов может кто угодно. Контейнеру имитатора тот же секрет передаётся
из `.env`, так что его вызовы проходят проверку.

Так же создаётся ключ маскирования персональных данных в журнале аудита
`AUDIT_MASK_KEY`: если его нет, он короче 32 символов или остался меткой,
`deploy.ps1` записывает случайный. Без ключа процесс в production не стартует.
Менять его без причины не нужно: отпечатки, снятые разными ключами, между
собой несравнимы, и по журналу перестанет быть видно, менялось ли поле.

Дополнительные настройки, у которых есть безопасные значения по умолчанию:
`TRUST_PROXY` — кому доверять `X-Forwarded-For` (по умолчанию частные сети
и локальный узел — так устроен стенд с Caddy на том же сервере);
`NOTIFY_TELEGRAM_API_URL`, `NOTIFY_MAX_API_URL` — адреса ботов мессенджеров,
которые из интерфейса больше не меняются.

Контейнеры получают только переменные, явно перечисленные в
`docker-compose.prod.yml`: строка в `.env`, которой там нет, до приложения
не доходит. Добавляя настройку, её нужно прописать и в образце, и в
compose-файле — у `api` и у `worker`.

Файл создаётся и правится только на сервере: пароли не должны проходить через
сборочный конвейер и не попадают в репозиторий. Домены в образце уже
проставлены, остальное при необходимости правится обычным блокнотом.

Первое развёртывание доставляет исходники и останавливается на отсутствии
`.env` — это нормальный порядок: доставка проходит, скрипт запускается,
настройки создаются один раз, следующий запуск идёт дальше.

### 5. Caddy

Фрагмент [Caddyfile.example](Caddyfile.example) уже настроен на домены
`incrment.ru` и `auth.incrment.ru` и на каталог `C:/www/incrment/current`.

```powershell
Copy-Item C:\www\incrment\repo\deploy\Caddyfile.example C:\caddy\sites\incrment.caddyfile
# в основном C:\caddy\Caddyfile один раз добавить: import sites/*.caddyfile
caddy validate --config C:\caddy\Caddyfile
caddy reload  --config C:\caddy\Caddyfile
```

Фрагмент копируется руками, поэтому после его изменения в репозитории копию на
сервере нужно обновить теми же командами. Последнее изменение — заголовки кэша:
`index.html` отдаётся с `no-cache` на любом маршруте интерфейса, а не только на `/`.

Записи DNS для обоих доменов должны указывать на сервер до перезагрузки Caddy —
иначе он не получит сертификаты. Если Caddy работает службой от LocalSystem,
доступ к `C:\www\incrment` у него уже есть; если от отдельной учётной записи —
дайте ей право на чтение каталога.

### 6. Секреты и переменные в GitHub

Settings → Secrets and variables → Actions.

| Секрет | Назначение |
|---|---|
| `SSH_HOST` | адрес сервера |
| `SSH_PORT` | порт SSH |
| `SSH_USER` | учётная запись развёртывания |
| `SSH_PRIVATE_KEY` | приватный ключ из шага 3 |
| `SSH_KNOWN_HOSTS` | необязательный: закрепляет ключ сервера |

| Переменная | Значение | Назначение |
|---|---|---|
| `PUBLIC_APP_URL` | `https://incrment.ru` | проверка стенда после развёртывания |
| `PUBLIC_AUTH_URL` | `https://auth.incrment.ru` | попадает в сборку фронтенда |
| `KEYCLOAK_REALM` | `rtk-crm` | то же |
| `KEYCLOAK_CLIENT_ID` | `crm-frontend` | то же |
| `FRONTEND_DATA_SOURCE` | `api` | источник данных интерфейса; `mock` — демо на моках, без обращения к API |
| `APP_DIR` | `C:/www/incrment` | если каталог другой |

Переменные, а не секреты: это не тайна, а часть сборки, и в журнале их видно
намеренно — иначе неверный адрес Keycloak пришлось бы искать вслепую.

Путь в `APP_DIR` пишется прямыми слэшами: значение проходит через bash на
раннере, где обратный слэш — знак экранирования.

## Первый запуск

Первое развёртывание поднимает всё само, но три момента требуют внимания.

**Docker Desktop должен быть запущен.** После перезагрузки сервера контейнеры
поднимутся только тогда, когда стартует сам Docker Desktop: `restart: unless-stopped`
работает внутри движка, а не вместо него. Включите автозапуск Docker Desktop
и автоматический вход в систему для учётной записи развёртывания — иначе стенд
будет молча лежать после каждой перезагрузки до первого входа руками.

**Keycloak.** Realm импортируется только при первом старте с пустой базой.
`deploy.ps1` подставляет в него домен стенда вместо `localhost`, поэтому вход
работает сразу. Дальнейшие изменения (новые пользователи, смена адресов
возврата) делаются в консоли администратора на `https://auth.incrment.ru` —
повторный импорт ничего не меняет. Пароль администратора Keycloak задаётся
в `.env` **до** первого старта: после создания базы он меняется только изнутри.

**ClamAV.** При первом запуске контейнер скачивает базы сигнатур — это несколько
минут. Пока он не готов, загрузка вложений отклоняется; всё остальное работает.

**Базовые процессы.** Процесс работы с вузом из 14 шагов и маршрут прямых продаж
приходят миграцией, а не наполнением: это часть поставки, описанная в техническом
задании. Свежеразвёрнутый экземпляр сразу позволяет заводить взаимодействия.
Если администратор опубликовал свою редакцию процесса, миграция её не трогает.

**Демонстрационные данные.** Заказчик реальных данных не предоставляет, поэтому
стенду нужен подготовленный набор: каталоги вузов, продуктов и направлений,
взаимодействия с историей переходов, тестовые пользователи. Наполнение выполняется
при каждой выкладке, если в `.env` задано:

```
SEED_DEMO_DATA=true
```

Шаг идемпотентен — существующие записи не трогаются, настроенный процесс
не подменяется, — поэтому повторные выкладки безопасны, а после пересоздания
тома базы данные восстанавливаются сами. На стенде с боевыми данными значение
обязательно `false`.

Разовый запуск вручную:

```powershell
cd C:\www\incrment\repo
docker compose -f deploy\docker-compose.prod.yml --env-file C:\www\incrment\.env `
  run --rm migrate npx prisma db seed
```

## Повседневные операции

```powershell
# короткая обёртка, чтобы не повторять пути
function dc { docker compose -f C:\www\incrment\repo\deploy\docker-compose.prod.yml --env-file C:\www\incrment\.env @args }

dc ps                        # состояние контейнеров
dc logs -f api               # журнал API
dc logs --tail 100 worker    # журнал фоновых задач
dc restart api worker        # перезапуск без пересборки
dc exec postgres psql -U crm -d crm    # консоль базы
```

Откат на прошлый выпуск — без пересборки и без участия GitHub:

```powershell
powershell -File C:\www\incrment\rollback.ps1              # что доступно
powershell -File C:\www\incrment\rollback.ps1 -Sha <sha>   # вернуться
```

Образы прошлых выпусков остаются на сервере с тегом по SHA, статика — в
`releases\web\<sha>` (хранятся последние пять).

## Если что-то пошло не так

**`docker ps` по SSH отвечает «cannot connect to the Docker daemon».** Сессия SSH
идёт под учётной записью, у которой нет своего сеанса Docker Desktop. См. шаг 2
подготовки сервера: разворачивать нужно под тем же пользователем, под которым
работает Docker Desktop.

**Ключ не принимается, хотя лежит в `authorized_keys`.** Учётная запись состоит
в администраторах — OpenSSH читает `C:\ProgramData\ssh\administrators_authorized_keys`
и требует строгих прав на этот файл (шаг 3).

**Сборка падает с «A specified logon session does not exist».** Docker Desktop
хранит учётные данные реестра в диспетчере учётных данных Windows, а тот привязан
к интерактивному входу: из сессии SSH помощник обращается к несуществующему
сеансу и не отдаёт ничего — даже для публичных образов, которым учётные данные
вовсе не нужны. Развёртывание обходит это само: берёт отдельную конфигурацию
Docker без помощника и явный адрес движка, личные настройки пользователя при
этом не трогает. Если ошибка всё же появилась, уберите `credsStore` из
`%USERPROFILE%\.docker\config.json` учётной записи развёртывания.

**Развёртывание упало на ожидании готовности API.** Скрипт уже откатил бэкенд на
предыдущий образ и не тронул статику. Причину видно в выводе задачи — там
последние 60 строк журнала API. Чаще всего это проверка конфигурации: она
намеренно роняет процесс при небезопасных настройках вместо тихого запуска
в ослабленном виде.

**Postgres не стартует, в журнале `/docker-entrypoint-initdb.d/10-keycloak-db.sh: line 2: $'\r': command not found`.**
Скрипт попал в контейнер с переводами строк Windows. В репозитории это
исключено правилом `*.sh text eol=lf` в `.gitattributes`; если файл правили
на сервере блокнотом — сохраните его заново с переводами строк LF.

**`CRM-AUT-0003` при входе.** Токен выпущен с одним адресом, а бэкенд ждёт
другой. Проверьте, что `PUBLIC_AUTH_URL` в `.env` совпадает с доменом, на
котором Caddy отдаёт Keycloak, и что в Caddy включён проброс `X-Forwarded-*`
(в примере конфигурации он есть).

**Вход ведёт на `localhost:5173`.** Realm импортировался раньше, чем в `.env`
появился нужный домен. Поправьте адреса возврата клиента `crm-frontend`
в консоли Keycloak — переимпорт realm на существующей базе не поможет.

**`incrment.ru` отвечает 404 вместо интерфейса.** Две причины, и обе видны сразу.
Либо фрагмент Caddy не подключён — проверьте `caddy validate --config C:\caddy\Caddyfile`
и наличие строки `import sites/*.caddyfile` в основном файле. Либо ещё не было
удачного развёртывания: каталог `C:\www\incrment\current` создаётся на последнем
шаге, и до тех пор отдавать Caddy нечего. Проверить: `dir C:\www\incrment\current`.

Автоматического перехода на страницу входа Keycloak нет и не задумано: интерфейс
открывает собственный экран входа с кнопкой и уводит к провайдеру по нажатию.
Пустая страница вместо него означает, что статика не разложена.

**На экране входа поля email и пароля и список тестовых аккаунтов.** Фронтенд собран
без адреса Keycloak и работает в демо-режиме, не обращаясь к API. Проверьте
переменную `PUBLIC_AUTH_URL` в настройках репозитория и перезапустите workflow —
без неё проверки теперь останавливаются ещё до сборки.

**После входа — «Не удалось получить профиль пользователя».** Keycloak выдал токен,
а `GET /api/v1/auth/me` не ответил: API не запущен (`dc ps`) либо Caddy не
проксирует `/api/*`. Токены при этом сохраняются — после восстановления API
достаточно обновить страницу.

**Keycloak требует одноразовый код при входе.** В экспорте realm у учётной записи
`admin.sidorov` стояло требование настроить OTP при первом входе. В репозитории оно
снято, но на уже поднятом стенде повторный импорт realm ничего не меняет — уберите
его в консоли: Users → admin.sidorov → Details → Required user actions → удалить
«Configure OTP» → Save. Чтобы закрыть тему для всего realm: Authentication →
Required actions → «Configure OTP» → выключить.

**Caddy отдаёт 502 на `/api/*`.** Контейнер API не запущен или слушает другой
порт: `dc ps` и проверка порта из раздела выше.

**Нужно освободить место.** `docker image prune -a` удалит и образы прошлых
выпусков — откат после этого потребует пересборки. Безопаснее удалять точечно:
`docker image rm incrment/api:<старый-sha>`.
